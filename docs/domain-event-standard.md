## 1. What Is a Domain Event

A **domain event** is a record that something operationally meaningful happened in the business domain. It captures a state transition, a decision, or an action that matters to the business — not how the system processed it technically.

### Definition

A domain event answers: *"What happened in the business?"* — not *"What happened in the HTTP layer?"*

#### Technical Log

```
POST /api/v1/tenders
returned HTTP 201
duration: 142ms
```

Records *how* the system processed the request. Framework-generated. Says nothing about what business action occurred.

#### Domain Event

```
tender.published
entity_id: TND-2026-0042
actor: procurement-officer
status: draft → published
```

Records *what* happened in the business. Developer-authored. An engineer reading this understands the business state change without knowing the API contract.

#### Metric

```
procurement_tenders_published_total{
  category="goods",
  method="open"
} 347
```

Records *how many* times it happened. Aggregated. No individual detail. Used for trends, alerting, dashboards.

### When Each Applies

| Question You're Answering | Use | Example |
|---|---|---|
| What HTTP status did the server return? | Technical log (SDK auto) | `request_complete status=201 duration_ms=142` |
| What business action did the user take? | Domain event | `tender.published entity_id=TND-2026-0042` |
| How many tenders were published this week? | Metric | `procurement_tenders_published_total` |
| Why did this specific tender fail to publish? | Domain event (error) | `tender.publish_failed reason=missing_required_lots` |
| Is the tender publish error rate above 5%? | Metric + alert | `rate(tender_publish_errors_total[5m]) / rate(tender_publishes_total[5m])` |

### When To Log a Domain Event

- An entity changes state (draft → published, pending → approved, active → cancelled)
- A business decision is made (bid accepted, credit score approved, payment authorized)
- A user performs an important action (submits a bid, publishes a tender, assigns an evaluator)
- An external system responds to a business request (payment gateway confirms, NID validation returns)
- An asynchronous process completes or fails (scheduled job finishes, notification delivery fails)
- A business rule prevents an action (insufficient funds, bid after deadline, unauthorized access to tender)

### When NOT to Log a Domain Event

- **CRUD without business significance** — fetching a list, reading a record, updating a timestamp
- **Technical operations** — database query executed, cache hit/miss, HTTP request received (SDK handles these)
- **High-frequency data flow** — every Kafka message consumed, every row processed in a batch (use metrics)
- **Intermediate computation steps** — validating field X, checking constraint Y (log the outcome, not the steps)

## 2. Domain vs Technical vs Metric

| Characteristic | Technical Log | Domain Event | Metric |
|---|---|---|---|
| Purpose | System debugging | Business process understanding | Aggregation, alerting, trending |
| Audience | SRE, platform engineer | SRE, developer, product owner | SRE, dashboards, alerts |
| Granularity | Per request/operation | Per business action | Counter / gauge / histogram |
| Generated by | SDK (automatic) | Developer (intentional) | SDK + developer |
| Queryable by | request_id, trace_id, service | entity_id, event_type, actor | Labels (service, status, category) |
| Cardinality | Bounded (routes × methods) | Bounded (event types × entity types) | Strictly bounded (labels only) |
| Storage | Loki | Loki (same pipeline) | Prometheus |
| Retention need | 7–30 days | 30–90 days (audit trail) | 30–90 days |
| Example | `request_complete POST /tenders 201` | `tender.published TND-2026-0042` | `tenders_published_total 347` |

> **Key insight:** Business importance ≠ log severity. A `tender.published` event is business-critical (it starts a public procurement process) but is a normal, expected operation — `INFO` level. A `tender.publish_failed` due to a validation error is a minor business hiccup — `WARN` level. Severity reflects *operational concern*, not *business value*.

## 3. Event Naming Convention

### Pattern

```
{entity}.{action}
```

or for nested entities:

```
{parent_entity}.{child_entity}.{action}
```

### Rules

| Rule | Standard | Example |
|---|---|---|
| Separator | Dot (`.`) | `tender.published` |
| Casing | All lowercase, snake_case for multi-word segments | `credit_score.calculated` |
| Tense | Past tense — events record what *happened* | `bid.submitted` not `bid.submit` |
| Entity naming | Singular noun matching domain model | `tender` not `tenders` |
| Action naming | Past participle describing the transition | `published`, `submitted`, `failed` |
| Failure events | `{entity}.{action}_failed` | `payment.authorization_failed` |
| Hierarchy depth | Max 3 levels | `tender.clarification.published` |
| No verbs as entities | Use nouns for entities | `evaluation.completed` not `evaluate.completed` |

### Standard Actions

| Action | Meaning | When to Use |
|---|---|---|
| `created` | Entity brought into existence | Only when creation is a meaningful business event, not every INSERT |
| `updated` | Entity modified (significant change) | Only for business-significant updates, not every field change |
| `deleted` | Entity removed | Rare. Prefer `cancelled`, `archived`, `deactivated` for soft deletes |
| `published` | Entity made visible/active/public | State transition from draft/private to public/active |
| `submitted` | Entity sent for processing/review | User action handing off to a process |
| `approved` | Entity accepted by authority | Decision point — approval workflow |
| `rejected` | Entity declined by authority | Decision point — denial with reason |
| `cancelled` | Entity voided/withdrawn | Business cancellation, not system error |
| `completed` | Process finished successfully | End of a multi-step operation |
| `failed` | Process could not complete | Business failure (not HTTP 500 — that's technical) |
| `expired` | Entity timed out | Deadline passed, session expired, offer expired |
| `assigned` | Entity given to an actor | Work assignment, role assignment |
| `started` | Process begun | Long-running operation initiated |

### Versioning

Events are not versioned in their name. Schema changes handled by adding optional fields — never removing or renaming existing fields. If an event's meaning fundamentally changes, create a new event name.

## 4. Standard Event Schema

```json
{
  // === SDK-populated (automatic) ===
  "time":           "2026-09-07T08:15:30.123Z",
  "level":          "info",
  "service_name":   "procurement-service",
  "environment":    "production",
  "version":        "2.1.0",
  "request_id":     "7b0c6fd6-a3f8-4c9d-b2e1-...",
  "correlation_id": "a3f8c9d2-7b0c-4fd6-...",
  "trace_id":       "4bf92f3577b34da6a3ce929d...",
  "span_id":        "00f067aa0ba902b7",

  // === Domain event fields (developer-supplied) ===
  "msg":            "tender.published",
  "event_category": "domain",

  "entity_type":    "tender",
  "entity_id":      "TND-2026-0042",

  "actor_type":     "user",
  "actor_id":       "USR-00451",

  "metadata": {
    "previous_status": "draft",
    "new_status":      "published",
    "tender_category": "goods",
    "procurement_method": "open",
    "lot_count":       3,
    "submission_deadline": "2026-10-15T17:00:00Z"
  }
}
```

### Field Classification

| Classification | Field | Source | Notes |
|---|---|---|---|
| **Required** | `time` | SDK auto | ISO 8601 UTC |
| **Required** | `level` | SDK auto | info / warn / error / debug |
| **Required** | `service_name` | SDK auto | From config |
| **Required** | `environment` | SDK auto | From config |
| **Required** | `msg` | Developer | Event name (`tender.published`) |
| **Required** | `event_category` | SDK auto | Always `"domain"` for domain events |
| **Required** | `entity_type` | Developer | What entity changed |
| **Required** | `entity_id` | Developer | Which instance |
| **Required** | `request_id` | SDK auto | From AsyncLocalStorage context |
| Recommended | `correlation_id` | SDK auto | Cross-service correlation |
| Recommended | `trace_id` | SDK auto | OTEL trace context |
| Recommended | `actor_type` | Developer | `user` / `system` / `scheduler` / `external` |
| Recommended | `actor_id` | Developer | Who triggered it (user ID, system name) |
| Recommended | `metadata.previous_status` | Developer | On state transitions |
| Recommended | `metadata.new_status` | Developer | On state transitions |
| Optional | `metadata.reason` | Developer | On rejections, failures, cancellations |
| Optional | `metadata.external_ref` | Developer | External system reference ID |
| Optional | `metadata.attempt` | Developer | Retry number |
| Optional | `metadata.duration_ms` | Developer | On completing operations |
| **Prohibited** | passwords, secrets, tokens | — | SDK redaction enforces |
| **Prohibited** | PII: national IDs, phone numbers | — | Developer discipline |
| **Prohibited** | Full request/response bodies | — | Use entity_id to look up in DB |
| **Prohibited** | Financial amounts in metadata | — | Log currency + range/bucket, not exact amount |
| **Prohibited** | Credit card numbers, bank accounts | — | Never, under any circumstance |

## 5. Severity Mapping

| Level | Business Meaning | Examples |
|---|---|---|
| `INFO` | Normal business operation completed successfully. Expected behavior. This is where 90% of domain events belong. | `tender.published`, `bid.submitted`, `payment.completed`, `evaluation.started`, `user.logged_in` |
| `WARN` | Unexpected business state that did not prevent the operation but indicates something unusual. Business rule violation. Approaching a limit. | `bid.submitted_after_deadline` (rejected), `payment.retry_needed`, `tender.no_bids_received`, `credit_score.below_threshold` |
| `ERROR` | Business operation failed. Something the business needs to address. Not the same as a system error — a 500 is a technical error; a payment declined by gateway is a business error. | `payment.authorization_failed`, `notification.delivery_failed`, `nid.validation_failed` (external service error), `settlement.batch_failed` |
| `DEBUG` | Domain detail useful only during development or specific investigations. Never enabled in production by default. | `evaluation.score_calculated` (intermediate step), `bid.validation_detail`, `workflow.step_entered` |

> ⚠️ **Business importance ≠ log severity.** A `tender.published` event starts a procurement worth millions — extremely business-critical. But it is a normal, successful operation → `INFO`. A `bid.submitted_after_deadline` is a minor rejection → `WARN`. Severity reflects *operational concern level*, not *dollar value*.

## 6. Metadata Standards

### Metadata by Event Type

| Event Pattern | Required Metadata | Recommended |
|---|---|---|
| State transition (`*.published`, `*.approved`, `*.cancelled`) | `previous_status`, `new_status` | `reason` (on cancellations/rejections), `actor_id` |
| Operation completed (`*.completed`) | `duration_ms`, `status` (success/partial/failed) | `result_count`, `items_processed` |
| External integration (`*.verified`, `*.synced`) | `external_system`, `external_ref` | `duration_ms`, `response_code` |
| Failure (`*_failed`) | `failure_reason` (enumerated), `error_code` | `attempt`, `will_retry`, `next_retry_at` |
| Assignment (`*.assigned`) | `assignee_id`, `assignee_type` | `previous_assignee_id` |
| Scheduled/async (`job.*`) | `job_name`, `job_type` | `schedule_expression`, `next_run_at` |

### Failure Reasons Are Enums

```typescript
// ❌ Free text — impossible to aggregate
failure_reason: error.message  // "ETIMEDOUT 10.0.0.5:3306"

// ✅ Enumerated — queryable, aggregatable
failure_reason: "provider_timeout"
error_code: "PAYMENT_GW_001"
// error.message goes in technical log, not domain event
```

Standard failure reason enums per domain:

| Domain | Failure Reasons |
|---|---|
| Payment | `insufficient_funds`, `card_declined`, `provider_timeout`, `provider_error`, `invalid_account`, `limit_exceeded`, `duplicate_transaction` |
| Auth | `invalid_credentials`, `account_locked`, `token_expired`, `mfa_failed`, `ip_blocked` |
| Procurement | `deadline_passed`, `missing_required_fields`, `insufficient_lots`, `budget_exceeded`, `duplicate_submission`, `unauthorized_action` |
| Credit | `data_unavailable`, `model_error`, `below_threshold`, `external_service_error` |
| Notification | `invalid_recipient`, `provider_error`, `template_error`, `rate_limited`, `channel_unavailable` |

## 7. Security & Privacy

### What Goes in Domain Event Metadata

| Data | Allow? | How |
|---|---|---|
| Entity IDs (tender_id, bid_id) | ✅ Yes | System identifiers are safe |
| Actor ID (user_id) | ✅ Yes | System identifier, not PII itself |
| Status transitions | ✅ Yes | Business state is operational data |
| Category/type labels | ✅ Yes | Low-cardinality classification |
| Counts (lot_count, item_count) | ✅ Yes | Aggregate numbers safe |
| Duration (duration_ms) | ✅ Yes | Performance data |
| Enumerated reasons | ✅ Yes | `failure_reason: "insufficient_funds"` |
| Email addresses | ❌ No | Log user_id, look up email in DB |
| Phone numbers | ❌ No | Never in logs |
| National ID numbers | ❌ No | Log validation result, not the number |
| Financial amounts | ⚠️ Bucket only | `amount_range: "100k-500k"` not exact value |
| Account numbers | ❌ No | Log last 4 digits or masked at most |
| Passwords, tokens, secrets | ❌ No | SDK redaction enforces |
| Full request/response bodies | ❌ No | Use entity_id to retrieve from DB |
| IP addresses | ⚠️ Security only | Only in auth events (`login_failed`) |

## 9. High-Volume Event Strategy

| Event Pattern | Volume Risk | Strategy | Reasoning |
|---|---|---|---|
| Every HTTP request | 🔴 Very High | **Metric only** (SDK auto). Log only on error. | SDK's `http_requests_total` counter covers aggregate. Technical `request_complete` log exists for individual requests. No separate domain event needed. |
| Every Kafka message consumed | 🔴 Very High | **Metric only**. Log failed processing only. | `kafka_messages_consumed_total` metric. Individual message processing logged only on error with topic, partition, error detail. |
| Every database query | 🔴 Very High | **Never as domain event**. Trace spans capture this. | OTEL DB instrumentation creates spans. Slow queries surface as span duration. No log needed. |
| Token refresh | 🟡 High | **Metric only** | `auth_tokens_refreshed_total`. Individual refresh has no investigative value. |
| Session expired | 🟡 High | **Metric only** | Count matters for capacity planning. Individual expiry is not actionable. |
| File downloaded | 🟡 High | **Metric only** | Track download counts, not individual events. Log only errors. |
| Configuration read | 🔴 Very High | **Never** | Only *changes* to configuration are events. Reads are routine. |
| Bid submitted | 🟢 Low | **Both log + metric** | Low volume (tenders per day), high business value. Every submission matters. |
| Payment initiated | 🟡 Medium | **Both log + metric** | Every payment is individually valuable for investigation. Metric for dashboards. |
| Login failed | 🟡 Medium (attack) | **Both**, with rate-limit protection | Each failure valuable for security investigation. Metric for alerting. Under brute force: sample logs, always count metric. |

### Volume Control Rules

1. **If event >100/second per service** → metric only, log on failure
2. **If event 1–100/second** → metric + sampled log (10–100%)
3. **If event <1/second** → both log + metric (full fidelity)
4. **Never log routine reads** — only state changes

### How Correlation Works

| ID | Scope | Set By | Propagated Via | Purpose |
|---|---|---|---|---|
| `request_id` | Single HTTP request | SDK ContextMiddleware (per request) | Not propagated — unique per service hop | Find all logs for one request within one service |
| `correlation_id` | Entire business operation | Gateway (or first service) via `x-correlation-id` | `x-correlation-id` header, Kafka message headers | Find all logs across all services for one business operation |
| `trace_id` | Distributed trace | OTEL TracerProvider | W3C `traceparent` header | Link to Tempo trace. See exact call graph and timing. |
| `entity_id` | Business entity lifetime | Developer | Included in domain event metadata | Find all events about one tender / bid / payment ever |

### Loki Correlation Queries

```logql
# All domain events for one business operation
{event_category="domain"} | json | correlation_id="a3f8c9d2-..."

# All events for one tender across all services
{event_category="domain"} | json | entity_id="TND-2026-0042"

# All events for one tender, ordered by time (lifecycle view)
{event_category="domain"} | json | entity_id="TND-2026-0042"
  | line_format "{{.time}} [{{.service_name}}] {{.msg}}"
```

## 11. Developer Guidelines

### DO

- Log meaningful state transitions: `tender.published`, `payment.completed`, `bid.rejected`
- Use enumerated `msg` values from the event catalog — never free text
- Include `entity_type` and `entity_id` — so someone can trace one entity's history
- Include `duration_ms` on every completing/finishing event
- Use enumerated `failure_reason` values — not `error.message`
- Record `previous_status` and `new_status` on every state transition
- Use `event_category: "domain"` to distinguish from technical logs in Loki
- Let the SDK populate `request_id`, `correlation_id`, `trace_id`, `service_name`, `time`
- Test that domain events appear in Loki for your service during development

### DON'T

- Log every function call, variable assignment, or validation step as a domain event
- Log every CRUD operation — an entity *read* is not an event
- Put entity_id, user_id, or request_id into metric labels (cardinality explosion)
- Log secrets, PII (national IDs, phone numbers, emails), or full request/response bodies
- Log exact financial amounts — use amount_range buckets
- Duplicate the same event across multiple services — log where the state change happens
- Invent new event names without adding them to the catalog
- Use free-text `msg` values like `"Payment for user X was processed"`
- Log technical errors as domain events — SDK `ObservabilityExceptionFilter` handles 5xx errors
- Use console.log for domain events — always go through SDK domain event API

## 12. Log vs Metric Decision Matrix

| Event Category | Examples | Log | Metric | Reason |
|---|---|---|---|---|
| Auth state changes | `login_succeeded`, `login_failed`, `account_locked` | ✓ | ✓ | Each occurrence is security-relevant (log). Aggregate rate needed for alerting (metric). |
| Payment operations | `payment.initiated`, `payment.completed`, `payment.authorization_failed` | ✓ | ✓ | Each payment matters for investigation (log). Error rate and throughput for dashboards (metric). |
| Tender lifecycle | `tender.published`, `tender.cancelled`, `tender.closed` | ✓ | ✓ | Low volume, high value. Both needed. |
| Bid operations | `bid.submitted`, `bid.rejected`, `bid.accepted` | ✓ | ✓ | Each bid is individually significant. Counts needed for procurement analytics. |
| Evaluation steps | `evaluation.score_submitted` | ✓ | — | Individual scores matter for audit trail. No aggregation value. |
| Token refresh | `auth.token_refreshed` | — | ✓ | Individual refresh has no investigative value. Volume matters. |
| Session expiry | `auth.session_expired` | — | ✓ | Rate matters for capacity. Individual is routine. |
| Job execution | `job.completed`, `job.failed` | ✓ | ✓ | Each job run matters for debugging (log). Duration/failure rate for alerting (metric). |
| Workflow steps | `workflow.step_completed` | ✓ | — | Individual step detail for debugging. Workflow-level metric suffices for aggregate. |
| Config changes | `config.updated`, `config.feature_toggled` | ✓ | — | Audit trail. Volume too low for meaningful metrics. |
| RBAC changes | `access.role_assigned`, `access.permission_denied` | ✓ | denied: ✓ | Role changes: audit only. Permission denied: rate alerting (brute force detection). |

## 13. SDK Design

### Proposed API

```typescript
import { ObservabilityLogger } from '@brdrwanda/observability';

class TenderService {
  constructor(private readonly logger: ObservabilityLogger) {}

  async publishTender(tenderId: string, actor: Actor): Promise<void> {
    const tender = await this.findTender(tenderId);

    // ... business logic ...

    // Domain event — one call, SDK handles the rest
    this.logger.domainEvent('tender.published', {
      entity_type: 'tender',
      entity_id: tenderId,
      actor_type: 'user',
      actor_id: actor.id,
      metadata: {
        previous_status: tender.status,
        new_status: 'published',
        tender_category: tender.category,
        procurement_method: tender.method,
        lot_count: tender.lots.length,
        submission_deadline: tender.deadline,
      },
    });
  }
}
```

### What the SDK Populates Automatically

| Field | Source |
|---|---|
| `time` | ISO 8601 UTC timestamp |
| `level` | Default `info`, developer can override |
| `service_name` | SDK config |
| `environment` | SDK config |
| `version` | SDK config |
| `event_category` | Always `"domain"` |
| `request_id` | AsyncLocalStorage context |
| `correlation_id` | AsyncLocalStorage context |
| `trace_id` | Active OTEL span |
| `span_id` | Active OTEL span |

### API Design

```typescript
interface DomainEventOptions {
  entity_type: string;           // REQUIRED
  entity_id: string;             // REQUIRED
  actor_type?: 'user' | 'system' | 'scheduler' | 'external';
  actor_id?: string;
  level?: 'debug' | 'info' | 'warn' | 'error';  // default: 'info'
  metadata?: Record<string, unknown>;
}

// On ObservabilityLogger:
domainEvent(eventName: string, options: DomainEventOptions): void;
```

### SDK Design Decisions

| Question | Decision | Reasoning |
|---|---|---|
| Dedicated `domainEvent()` API? | ✅ Yes | Sets `event_category: "domain"` automatically. Enforces required fields. Distinguishes from `logger.info()`. |
| Enforce event naming convention? | ✅ Yes — validate format | SDK validates `{entity}.{action}` pattern. Warn in dev, pass-through in prod (don't crash service). |
| Automatically create metrics? | ⚠️ No — opt-in | Auto-creating a counter per event risks cardinality. Metrics should be explicitly defined by developers who understand label cardinality. |
| Correlation IDs inherited? | ✅ Yes — automatic | SDK reads `request_id`, `correlation_id`, `trace_id` from AsyncLocalStorage. Developer never sets these manually. |
| Sensitive data filtering? | ✅ Yes — SDK redaction | Same Pino redaction paths apply. Metadata goes through redaction. But domain PII (NID, phone) requires developer discipline — SDK can't know which custom fields are sensitive. |
| Schema versioning? | ⚠️ Not yet | Over-engineering at current scale. Add optional `event_version` field when schema evolution becomes a problem. |
| Invalid event handling? | ✅ Warn, don't crash | In dev: log warning about invalid event name or missing fields. In prod: emit event as-is (observability must not break the application). |
| Service-specific events without SDK changes? | ✅ Built-in | `domainEvent()` accepts any `eventName` string. SDK validates format, not a whitelist. Services define their own events freely. |

### Implementation Sketch

```typescript
// In logger.service.ts — add to ObservabilityLogger class

domainEvent(eventName: string, options: DomainEventOptions): void {
  // Validate event name format in development
  if (this.environment !== 'production') {
    const pattern = /^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){1,2}$/;
    if (!pattern.test(eventName)) {
      this.warn({
        msg: 'invalid_domain_event_name',
        event_name: eventName,
        expected_pattern: '{entity}.{action}',
      });
    }
    if (!options.entity_type || !options.entity_id) {
      this.warn({
        msg: 'domain_event_missing_required_fields',
        event_name: eventName,
        missing: [
          !options.entity_type && 'entity_type',
          !options.entity_id && 'entity_id',
        ].filter(Boolean),
      });
    }
  }

  const level = options.level || 'info';

  this[level]({
    msg: eventName,
    event_category: 'domain',
    entity_type: options.entity_type,
    entity_id: options.entity_id,
    actor_type: options.actor_type,
    actor_id: options.actor_id,
    metadata: options.metadata,
    // request_id, correlation_id, trace_id
    // automatically injected by Pino mixin from AsyncLocalStorage
  });
}
```

## 14. Open Decisions

1. **Procurement data model validation** — Tender, bid, lot, evaluation, award entity names and status values need confirmation from procurement domain owner. Events above follow OCDS-aligned naming.
2. **CRM entity model** — crm-main's entity model (leads? contacts? opportunities?) needs investigation. Events are speculative.
3. **mel-service, giwawe-microservice, logging-microservice** — Business domains completely unknown. Cannot define events without domain investigation.
4. **ibank-service operations** — Full banking operation set (beyond transfers) needs confirmation. Statements, account management, loan operations?
5. **export-finance workflows** — Letters of credit? Export guarantees? Trade documents? Service crash-looping — stabilize first.
6. **Financial amount logging policy** — Current recommendation: log amount_range buckets, never exact amounts. Confirm this meets both operational and compliance requirements.
7. **Domain event retention** — Should domain events with `event_category: "domain"` have longer Loki retention than technical logs? (30 days vs 90 days for audit)
8. **Event catalog registry** — Should there be a central YAML/JSON file listing all valid event names per service, checked at build time? Or is runtime format validation sufficient?
9. **Auto-metric from domain events** — Current decision: no automatic counter per event. Revisit if developers consistently forget to create matching Prometheus metrics.
10. **Notification service** — Is notification handling part of workflow-service, or is there a dedicated notification service? Events above assume workflow-service handles it.
11. **Kafka event correlation** — How is `correlation_id` propagated through Kafka message headers? SDK may need explicit Kafka header injection/extraction support.
