Domain Event Logging v2.0.0

Domain events capture business state transitions — what happened in the system from a business perspective. They are separate from technical HTTP logs (which the SDK handles automatically) and from ad-hoc logger.info() calls.

When to use domainEvent() vs logger.info(): Use domainEvent() for business actions that stakeholders care about — login, tender published, payment processed, bid submitted. Use logger.info() for technical details — cache hit, query executed, retry attempt.

Quick Start

import { ObservabilityLogger } from '@brdrwanda/observability';

@Controller('api/users')
export class UsersController {
  constructor(private logger: ObservabilityLogger) {}

  @Post('login')
  async login(@Body() dto: UserLoginDto) {
    try {
      const result = await this.authService.authenticate(dto);

      this.logger.domainEvent('auth.login_succeeded', {
        entity_type: 'session',
        entity_id: result.sessionId,
        actor_type: 'user',
        actor_id: result.userId,
        metadata: {
          auth_method: 'standard',
          client_app: 'http://tugane-main.brd.rw',
        },
      });

      return result;
    } catch (error) {
      this.logger.domainEvent('auth.login_failed', {
        entity_type: 'auth_attempt',
        entity_id: dto.username,
        actor_type: 'user',
        level: 'warn',
        metadata: {
          failure_reason: 'invalid_credentials',
          auth_method: 'standard',
        },
      });
      throw error;
    }
  }
}

API Reference

domainEvent(eventName, options)

Log a structured business event. The SDK automatically injects service context, request correlation, and trace IDs.

Parameters

Parameter Type Required Description
eventName string Yes Dot-separated event name: {entity}.{action}

DomainEventOptions

Field Type Required Description
entity_type string Yes Business entity type — 'tender', 'payment', 'session', 'bid'
entity_id string Yes Specific instance ID — 'TND-2026-0042', 'PAY-00891'
actor_type ActorType No Who triggered: 'user' | 'system' | 'scheduler' | 'external'
actor_id string No Actor identifier — user ID, system name, cron job name
level LogLevel No Override log level. Default: 'info'. Use 'warn' for failures.
metadata Record<string, unknown> No Domain-specific context for troubleshooting

Types

import { DomainEventOptions, ActorType } from '@brdrwanda/observability';

type ActorType = 'user' | 'system' | 'scheduler' | 'external';

interface DomainEventOptions {
  entity_type: string;
  entity_id: string;
  actor_type?: ActorType;
  actor_id?: string;
  level?: 'debug' | 'info' | 'warn' | 'error' | 'fatal';
  metadata?: Record<string, unknown>;
}

Event Naming Convention

Event names follow the pattern {entity}.{action} using lowercase snake_case:

Pattern Examples
{entity}.{action} tender.published, bid.submitted, auth.login_succeeded
{entity}.{sub}.{action} tender.evaluation.completed, loan.disbursement.failed

The regex pattern enforced in development:

^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){1,2}$

Dev-mode validation: In non-production environments, the SDK warns (but does not crash) on invalid event names and missing entity_type/entity_id. No validation runs in production — zero overhead.

Auto-injected fields

These fields are added by the SDK — you never pass them manually:

Field Source Purpose
event_category auto Always "domain" Separates domain events from technical logs in Loki
service_name auto SDK config Which microservice emitted the event
environment auto SDK config / NODE_ENV Production, staging, development
version auto SDK config Service version for tracking regressions
request_id auto X-Request-Id header or generated Unique per HTTP request
correlation_id auto X-Correlation-Id header or request_id Tracks a request across services
trace_id auto OpenTelemetry active span Links logs to distributed traces
span_id auto OpenTelemetry active span Specific span within the trace
client_app auto X-Client-App, Origin, or Referer Which frontend app made the request

Querying Domain Events in Loki

The event_category: "domain" field makes domain events instantly filterable:

All domain events

{service_name=~".+"} | json | event_category="domain"

Domain events from one service

{service_name="authentication-service"} | json | event_category="domain"

Specific event type

{service_name="authentication-service"} | json | event_category="domain" |= "auth.login_failed"

All events for one entity

{service_name=~".+"} | json | event_category="domain" | entity_id="TND-2026-0042"

Failed logins in the last hour

{service_name="authentication-service"} | json | event_category="domain" |= "auth.login_failed" | metadata_failure_reason="invalid_credentials"

All actions by one user

{service_name=~".+"} | json | event_category="domain" | actor_id="USR-00451"

Correlate domain event with its HTTP request

{service_name="authentication-service"} | json | request_id="d4a449ad-1ed0-417b-92f0-99648aa47087"

This returns the domain event, the request_complete log, and any request_error — all from the same HTTP request, correlated by request_id.

Domain Events vs Technical Logs

A single HTTP request can produce both types. Here's what a POST /api/users/login that fails generates:

Order Level Message Type Source
1 WARN auth.login_failed Domain event Your code (domainEvent())
2 WARN request_error Technical SDK exception filter (auto)
3 INFO request_complete Technical SDK interceptor (auto)

All three share the same request_id, correlation_id, and trace_id. In Loki, filter by event_category="domain" to see only business events, or by request_id to see the full picture for one request.

Best Practices

Do

  • Use entity_type + entity_id to identify what was affected
  • Use actor_type + actor_id to identify who did it
  • Set level: 'warn' for business failures (login failed, validation rejected, limit exceeded)
  • Set level: 'error' for broken business flows (disbursement failed, integration timeout)
  • Include previous_status and new_status in state transitions
  • Include failure_reason as a short enum value, not a free-text message
  • Keep metadata flat — avoid deeply nested objects

Don't

  • Don't log PII in entity_id — use internal IDs (USR-00451), not names or emails
  • Don't log passwords, tokens, or credit card numbers in metadata
  • Don't duplicate what the SDK auto-logs — no need to log HTTP method, status code, or duration in your domain event
  • Don't use domainEvent() for technical events — use logger.info() for cache hits, retries, query timing
  • Don't use free-text event names — tender.published not "Tender was published by user"

Metadata Guidelines

The metadata object carries domain-specific context. Keep it focused on what you'd need to troubleshoot or audit:

Event Recommended metadata
State transitions previous_status, new_status, reason
Financial events amount, currency, account_id (masked)
Auth events auth_method, client_app, failure_reason
Batch operations total_count, success_count, failure_count
Scheduled jobs job_name, duration_ms, items_processed

Redaction applies to metadata. The SDK's Pino redaction paths (*.password, *.token, etc.) apply to metadata fields too. If you include a field named token in metadata, it will be redacted to [REDACTED].

Standalone Mode

Domain events work in standalone mode too — for scripts, workers, and CLI tools outside NestJS:

import { createObservability } from '@brdrwanda/observability/standalone';

const obs = createObservability({
  serviceName: 'data-migration-worker',
  environment: 'production',
  version: '1.0.0',
});

obs.logger.domainEvent('migration.batch_completed', {
  entity_type: 'migration_batch',
  entity_id: 'BATCH-2026-042',
  actor_type: 'scheduler',
  metadata: {
    table: 'transactions',
    rows_migrated: 50000,
    duration_ms: 12345,
  },
});

Note: In standalone mode, request_id, correlation_id, and client_app are not auto-injected (there is no HTTP request). trace_id and span_id are injected if tracing is enabled.
